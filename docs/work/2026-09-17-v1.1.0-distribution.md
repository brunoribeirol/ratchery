# Work Plan: v1.1.0 distribution

## Objective

Turn the already-merged community-first onboarding into one immutable, verified
`v1.1.0` release, then use that exact release as the only input to the Homebrew tap.

## Non-goals

- Do not add another provider, memory backend, external runtime dependency, or agent.
- Do not create a moving major tag or modify either published v1.0 tag.
- Do not claim an OpenSSF Best Practices level before the maintainer submits and the
  service awards it.

## Assumptions and affected contracts

- `main` at `ec5ebe7` is the protected merge containing the community-first delta.
- `VERSION`, both hook copies, `MANIFEST.json`, release notes, Action documentation,
  archive names, and signed tag must agree on `1.1.0`.
- Homebrew must consume the published archive and checksum, never a branch snapshot or
  the interactive source installer.

## Risks

- Tagging before hosted checks or the client canary would publish an unverified tree.
- A stale tracked hook would make the source checkout enforce different code from the
  framework it publishes.
- Creating the tap before the release would require an unverified or mutable source URL.
- Reusing broad GitHub credentials for tap automation would expand supply-chain risk.

## Acceptance criteria and evidence paths

1. Every release identity surface reports `1.1.0`; the manifest verifier and archive
   builder reject drift. Evidence: targeted version searches, manifest verification,
   and release smoke.
2. `.agents/runtime/agent_workspace.py` equals `lib/hook_runtime.py`. Evidence: a unit
   regression test plus `cmp`.
3. Source and artifact behavior remain dependency-free and core-only setup works.
   Evidence: `make test` and `make release-smoke`.
4. The exact merged commit passes six CI jobs, CodeQL, and all five client-canary jobs.
   Evidence: hosted check/run IDs recorded before tagging.
5. The signed tag points to that commit and all four release assets plus both
   attestations verify. Evidence: Git/GPG, checksums, release API, and `gh attestation
   verify` outputs summarized in publication evidence.
6. The tap formula, created only afterward, pins the release URL/checksum and passes
   functional setup/doctor tests on supported Homebrew runners.

## Verification budget and stop conditions

Run targeted unit/version checks first, then the full suite and release smoke once the
manifest is final. Stop before a tag if any hosted gate is missing/failing, the remote
`main` changes unexpectedly, or repository visibility prevents CodeQL/attestations.
Stop Homebrew publication if the release asset or checksum cannot be independently
verified. External memory experiments begin only after distribution is complete.

## Next boundary

After `v1.1.0` and Homebrew are verified, prepare the OpenSSF application evidence for
maintainer submission. A separate `experiment/team-memory-backend` change may then test
one pinned `ai-memory` release under loopback/zero-provider/no-automatic-capture defaults;
it is not part of this release.
